## User and measured gap

Agent application engineers need to know whether a remote tool's idempotency contract
survives response loss, parameter changes, and retention expiry. Version 0.1 bypassed
an HTTP boundary and retained keys forever. An in-process exception is insufficient
evidence that the server committed before the client lost a response.

## Scope and architecture

Add `resumeprobe http-run` and `http-audit` with a versioned suite separate from the 0.1
process-crash schema. The supervisor starts an ephemeral IPv4 loopback HTTP server in
a distinct subprocess; the server owns its SQLite effect ledger. A fresh client
subprocess sends a bounded JSON POST. On the first request, the server commits and
closes the socket without status or body. A second client process retries.

Five named scenarios: no key; stable key; key regenerated by retry; stable key after
explicit simulated retention prune; stable key with changed payload. Pruning happens
through an internal supervisor-owned database call after the first client has exited,
never through a public admin endpoint. It deletes only test keys and preserves effects.
No wall-clock sleep, artificial backdating, or provider-retention-duration claim.

The server accepts only a fixed path, bounded content length, JSON object schema,
nonempty bounded operation IDs, optional bounded idempotency header, and synthetic
payloads. It binds only 127.0.0.1, uses no paid API, rejects chunked framing and non-finite
JSON, has socket/read timeouts, and shuts down owned subprocesses in finally blocks.
Output directories are exclusive and never overwrite existing user content.

The existing ledger gains an explicit keyed apply interface and atomic fixture-key prune,
without changing the 0.1 mode semantics. Key reuse binds both operation ID and payload;
different operations with identical payloads must not share a result. Preserve the
original process-crash report and its results.

## Acceptance and comparison

- Three repetitions each, fifteen end-to-end socket-loss experiments.
- Prove server PID differs from both client PIDs; client PIDs differ; durable effect
  event precedes dropped-response event; first client observes a transport error.
- No-key, regenerated-key, and pruned-key scenarios commit two effects despite successful
  retry (completion-only false safe). Stable retained keys commit one and return its ID.
- Changed payload retry returns HTTP 409, keeps one original effect, and does not report
  successful completion. Safe rejection is distinct from workflow completion.
- Evidence auditor recomputes identities, counts, payloads, event order, HTTP outcomes,
  and suite expectations; malformed input and stored verdict/summary tampering fail.
- Preserve raw JSON, static HTML, and an SVG with observed counts; browser QA desktop/mobile.
- Add concurrent HTTP same-key checks and protocol-failure input tests.
- All 0.1 tests still pass; Ruff, build, no-dependency clean wheel, README style checks.
